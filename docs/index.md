`sphinx-config-schema` is a [Sphinx](https://www.sphinx-doc.org) extension that renders a [JSON schema](https://json-schema.org) as a copyable TOML, YAML, or JSON example. Each key in the example shows the description of that setting as a tooltip, via [`sphinx-tippy`](https://github.com/sphinx-extensions2/sphinx-tippy), and links to itself so that it can be shared as a permalink.

This is useful for tools that read their configuration from a file, such as a `[tool.*]` table in `pyproject.toml`, and that generate a JSON schema for it, for instance for editor completion.

## Installation

```bash
pip install sphinx-config-schema
```

Then add the extension to the [`extensions`](https://www.sphinx-doc.org/en/master/usage/configuration.html#confval-extensions) list in your [`conf.py`](https://www.sphinx-doc.org/en/master/usage/configuration.html). It loads `sphinx_tippy` automatically:

```{code-block} python
:caption: conf.py
extensions = [
    "sphinx_config_schema",
]
```

## Usage

The {rst:dir}`config-schema` directive takes the path to a JSON schema file, relative to the current document or, with a leading `/`, to the documentation source directory. The optional {rst:dir}`table <config-schema:table>` option sets the dotted path of the table under which the settings appear, {rst:dir}`caption <config-schema:caption>` adds a caption to the code block, and {rst:dir}`format <config-schema:format>` selects the output format:

:::::{tab-set}

::::{tab-item} MyST
:sync: myst

````md
```{config-schema} example.schema.json
:caption: pyproject.toml
:table: tool.example
:format: toml
```
````

::::{tab-item} reST
:sync: rst

```rst
.. config-schema:: example.schema.json
    :caption: pyproject.toml
    :table: tool.example
    :format: toml
```

The {rst:dir}`format <config-schema:format>` option renders the example as `yaml` or `json` instead of the default `toml`. Settings are then nested by indentation instead of grouped under table headers. The tabs below show the same {{ example_schema }} in each format. Hover over a key to see what it does:

::::{tab-set}

:::{tab-item} TOML

```{config-schema} example.schema.json
:caption: pyproject.toml
:table: tool.example
:header-titles:
```

:::

:::{tab-item} YAML

```{config-schema} example.schema.json
:caption: config.yaml
:format: yaml
:name: settings
```

:::

:::{tab-item} JSON

```{config-schema} example.schema.json
:caption: config.json
:format: json
```

:::

The schema controls how the configuration is rendered:

- Each setting shows its `default` or, if it has no usable default, its first non-null example or enum choice. Enum choices are also collected from `anyOf` and `oneOf` alternatives and local `$ref` references, unless an alternative accepts any value of its type, as in a nullable boolean. An empty list or table default counts as a placeholder and yields to an example. Settings without a usable value are omitted, or reported as errors when the {rst:dir}`strict <config-schema:strict>` flag is enabled.

- A free-form table, an object with `additionalProperties` but no `properties`, shows its default or example like any other setting, such as {cfg}`.tool.example.server.headers`. Without one, it appears as an empty table, such as {cfg}`.tool.example.env`, so that readers see that it exists.

- Settings with a `null` default keep that default in YAML and JSON. Since TOML has no null value, the example is commented out there, so copying the block does not enable an optional setting. For instance, {config-schema:option}`index:tool.example.color-toml` has a nullable enum and a `null` default, so the TOML tab shows `# color = "auto"`.

- Objects with their own `properties` become nested tables, including objects reached through local `$ref` references such as those generated by [pydantic](https://docs.pydantic.dev).

- Each key has a tooltip containing its `description`, its actual default, allowed enum values, and any examples other than the value shown. Double backticks in descriptions render as inline code. The tooltip of the last component of the {rst:dir}`table <config-schema:table>` path shows the schema's top-level `description`.

- Keys listed under `required` get an asterisk<span class="config-schema-required"></span> in the example and a <span class="config-schema-badge">required</span> badge in their tooltip, such as {cfg}`.tool.example.server.host`. The asterisk is not copied with the example. Both can be restyled through the `config-schema-required` and `config-schema-badge` CSS classes.

- Each key links to itself and can be [referenced](#referencing-options).

### Referencing options

Use the {rst:role}`config-schema:option` role or its short alias {rst:role}`cfg` to link to an option. Both render the key as inline code and, without an explicit title, use the key path below the {rst:dir}`table <config-schema:table>` as the title, such as {config-schema:option}`index:tool.example.server.host-toml`. A reference to the table itself shows its full path, even if the table has no settings of its own and only appears in the headers of its subtables. With the {rst:dir}`header-titles <config-schema:header-titles>` flag, references to the tables of a TOML example show their header instead, such as {cfg}`.tool.example` for the TOML tab above. The standard [`ref`](https://www.sphinx-doc.org/en/master/usage/referencing.html#role-ref) role accepts the same labels but needs an explicit title and renders it as plain text, as in {ref}`the output option <index:tool.example.output-toml>`. Unnamed examples use labels qualified by the document name and the format:

The full {rst:dir}`table <config-schema:table>` path remains part of each label, with dots separating the levels of the hierarchy and a hyphen before the format. Repeated examples with the same format on one page receive numeric suffixes, such as `index:output-yaml-2`. These references resolve to {config-schema:option}`index:tool.example.output-toml` in the TOML tab and {config-schema:option}`index:output-json` in the JSON tab above.

Set {rst:dir}`name <config-schema:name>` to give an example a stable namespace instead. The YAML tab above does this with `:name: settings`, so its {config-schema:option}`settings.output` option is referenced with:

:::::{tab-set}

::::{tab-item} MyST
:sync: myst

```md
{config-schema:option}`settings.output`
```

::::

::::{tab-item} reST
:sync: rst

```rst
:config-schema:option:`settings.output`
```

::::

:::::

As in Sphinx's Python domain, a [leading `.`](https://www.sphinx-doc.org/en/master/usage/domains/python.html#cross-referencing-python-objects) matches every label whose key path ends with the target, and [`~`](https://www.sphinx-doc.org/en/master/usage/referencing.html#syntax) shortens the title to the last key. For instance, `` {cfg}`.tool.example.server.host` `` renders as {cfg}`.tool.example.server.host` and `` {cfg}`~.tool.example.server.host` `` as {cfg}`~.tool.example.server.host`, where `tool.example` selects the TOML tab over the YAML and JSON tabs.

When a suffix matches several labels, those on the current page take precedence, followed by those whose complete key path equals the target. If several candidates remain, Sphinx warns and lists them. Targets without a leading dot are exact labels. In both cases, keys can be spelled as in the schema, such as `log_level`, or as in the label, such as `log-level`.

When the [PyData Sphinx Theme](https://pydata-sphinx-theme.readthedocs.io) or a theme derived from it is used, the tooltips take its colors and follow light and dark mode.

### Other output formats

The example is built from regular docutils nodes, so it also appears in other output formats, such as plain text and LaTeX. There, each key becomes a label that can be referenced. In LaTeX output, the example is a highlighted code block with its caption, like any other code block. Tooltips only appear in HTML. Instead of the asterisk, the line of a required key ends in a `# required` comment, except in JSON, which has no comments.

## Directive reference

````{rst:directive} .. config-schema:: path
Render the JSON schema at `path` as a configuration example. The path is relative to the current document or, with a leading `/`, to the documentation source directory.

```{rst:directive:option} caption: text
:type: text

Caption of the code block, typically the name of the configuration file.
```

```{rst:directive:option} format: toml, yaml or json
:type: ``toml`` (default), ``yaml`` or ``json``

Serialization format of the example.
```

```{rst:directive:option} header-titles
:type: flag

Title references to the tables of a TOML example with their header, such as `[tool.example.server]`, instead of the key path. Has no effect in YAML and JSON, which have no table headers.
```

```{rst:directive:option} name: text
:type: text

Name the example so it can be referenced with an explicit title using the {rst:role}`config-schema:option` role. Option and nested-table labels use this name as a prefix instead of adding a format suffix. Names must be unique across the documentation; reusing a name on the same page produces a warning.
```

```{rst:directive:option} strict
:type: flag

Report settings that have no `default`, `examples`, or `enum` as an error instead of leaving them out.
```

```{rst:directive:option} table: dotted.path
:type: text

Dotted path of the table under which the settings appear, such as `tool.example`.
```
````

```{rst:role} config-schema:option
Link to a key of a {rst:dir}`config-schema` example as inline code. See [Referencing options](#referencing-options) for label syntax and title formatting.
```

```{rst:role} cfg
Short alias of {rst:role}`config-schema:option`.
```
